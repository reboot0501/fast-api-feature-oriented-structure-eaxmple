# FastAPI 애플리케이션 생성 방식 및 실무 아키텍처 비교

FastAPI 애플리케이션의 인스턴스 생성 구조, 수명주기(Lifespan)를 통한 데이터베이스 초기화, 실행 스크립트의 구성 방식을 살펴보고, **개발/프로토타입 단계**와 **실무 운영(Production) 환경**의 차이점 및 모범 사례를 정리한 문서입니다.

---

## 1. 애플리케이션 인스턴스 생성 방식 비교

### 방식 1. 전역 인스턴스 생성 방식 (현재 프로젝트 적용 방식)

`app/app.py`에서 `app = FastAPI(...)` 인스턴스를 전역(Global) 변수로 생성하고 라우터를 등록한 뒤, `app/main.py`에서 이를 import하여 실행 진입점으로 삼는 구조입니다.

```
┌─────────────────────────────────┐
│           app/app.py            │
│  - FastAPI 인스턴스 전역 생성     │
│  - 라우터(Router) 조립 및 등록   │
│  - lifespan (DB 초기화 등) 정의 │
└────────────────┬────────────────┘
                 │ from app.app import app
┌────────────────▼────────────────┐
│          app/main.py            │
│  - sys.path 및 .env 환경변수 로드│
│  - 루트(/) 엔드포인트 등록      │
│  - uvicorn CLI 진입점 제공      │
└─────────────────────────────────┘
```

#### 코드 예시
```python
# app/app.py
from fastapi import FastAPI
from route.signup import signup_flow_router, signup_fetch_router
from route.organiztion import organization_flow_router, organization_fetch_router

app = FastAPI(title="Fast API Feature Oriented Structure")

app.include_router(signup_flow_router)
app.include_router(signup_fetch_router)
app.include_router(organization_flow_router)
app.include_router(organization_fetch_router)
```

```python
# app/main.py
from app.app import app

@app.get("/")
def read_root():
    return {"message": "Welcome to FastAPI Feature-Oriented Example!"}
```

* **장점**:
  1. 구조가 직관적이고 설정 코드가 간결합니다.
  2. Uvicorn 실행 시 `"app.main:app"` 문자열 경로로 쉽게 바인딩할 수 있습니다.
* **단점**:
  1. **테스트 격리 한계**: `pytest` 등으로 단위/통합 테스트를 실행할 때, 이미 생성된 단일 전역 `app` 인스턴스를 공유하므로 테스트 케이스마다 독립된 환경(Test DB, Mock 세션 등)을 주입하기 까다롭습니다.
  2. **환경별 동적 구성 한계**: 개발(Dev), 검증(Staging), 운영(Prod) 환경에 따라 미들웨어나 플러그인을 조건부로 다르게 붙이기 어렵습니다.

### 방식 2. 애플리케이션 팩토리(Application Factory) 패턴 (실무 표준)

FastAPI 애플리케이션 객체를 직접 전역에 생성하지 않고, **`create_app()`이라는 팩토리 함수를 호출하여 생성**하는 패턴입니다.

```
┌──────────────────────────────────────────────┐
│             app/factory.py                   │
│                                              │
│   def create_app(settings=None) -> FastAPI:  │
│       - 환경별 설정(Dev/Prod/Test) 주입      │
│       - FastAPI 인스턴스 신규 생성           │
│       - 미들웨어(CORS, Auth, Log) 동적 연결  │
│       - 라우터 및 Lifespan 일괄 등록         │
│       return app                             │
└──────────────────────┬───────────────────────┘
         ┌─────────────┴─────────────┐
         ▼                           ▼
┌──────────────────┐       ┌──────────────────┐
│   app/main.py    │       │  tests/conftest  │
│ (운영/개발 서버) │       │   (Pytest 격리)  │
│ app=create_app() │       │ app=create_app() │
└──────────────────┘       └──────────────────┘
```

#### 코드 예시
```python
# app/factory.py
from fastapi import FastAPI
from app.config.settings import Settings, get_settings
from route.signup import signup_flow_router, signup_fetch_router
from route.organiztion import organization_flow_router, organization_fetch_router

def create_app(settings: Settings | None = None) -> FastAPI:
    if settings is None:
        settings = get_settings()

    app = FastAPI(
        title=settings.APP_TITLE,
        lifespan=lifespan,
    )

    # 1. 공통 미들웨어 등록 (CORS, Request ID, Logging 등)
    register_middlewares(app, settings)

    # 2. 전역 예외 처리기 등록 (Custom Exception Handlers)
    register_exception_handlers(app)

    # 3. 라우터 일괄 등록
    app.include_router(signup_flow_router)
    app.include_router(signup_fetch_router)
    app.include_router(organization_flow_router)
    app.include_router(organization_fetch_router)

    return app
```

```python
# app/main.py
from app.factory import create_app

app = create_app()

@app.get("/")
def read_root():
    return {"message": "Welcome to FastAPI Feature-Oriented Example!"}
```

* **장점**:
  1. **테스트 환경 격리**: 테스트 코드(`conftest.py`)에서 `create_app(test_settings)`를 호출하여 인메모리 SQLite나 테스트용 Mock 세션이 주입된 깨끗한 `app` 인스턴스를 매 테스트마다 생성할 수 있습니다.
  2. **환경별 동적 세팅**: `DEBUG=True`일 때만 Swagger UI(`/docs`)를 켜고, 운영 환경에서는 보안을 위해 비활성화(`docs_url=None`)하는 등의 조건부 분기가 깔끔해집니다.

## 2. 수명주기(Lifespan)와 데이터베이스 테이블 생성 방식 비교

### 방식 A. `lifespan` 내 `Base.metadata.create_all()` 자동 생성 (현재 방식)

```python
@asynccontextmanager
async def lifespan(app: FastAPI):
    """startup: 테이블 없으면 생성, 있으면 데이터 유지"""
    Base.metadata.create_all(bind=engine)
    print("[OK] Database tables created")
    yield
    """shutdown"""
    print("[INFO] Application is shutting down")
```

#### ① 적합한 상황
* 프로젝트 초기 프로토타입 개발 단계
* 로컬 개발 환경에서 빠르게 도메인 모델과 테이블을 검증할 때
* 테스트 환경에서 일회성 SQLite DB를 메모리에 띄워 검증할 때

#### ② 실무 운영 환경에서 사용하지 않는 이유
1. **스키마 변경(ALTER TABLE) 감지 불가**:
   * `create_all()`은 "테이블이 없으면 CREATE"만 수행합니다.
   * 실무에서는 테이블을 새로 만드는 것보다 기존 테이블의 **컬럼 추가/삭제, 컬럼 길이 변경, 인덱스 생성, 제약조건 수정**이 90% 이상입니다. `create_all()`은 이러한 스키마 변경 사항을 전혀 반영하지 못합니다.
2. **DB 접근 보안 권한 위배 (최소 권한 원칙)**:
   * 실무 운영 환경의 백엔드 서비스 DB 계정은 DML(`SELECT`, `INSERT`, `UPDATE`, `DELETE`) 권한만 가져야 합니다.
   * DDL(`CREATE`, `ALTER`, `DROP`) 권한을 애플리케이션 계정에 부여하는 것은 심각한 보안 취약점입니다.
3. **무중단 배포(Zero-Downtime) 시 동시성 충돌**:
   * 쿠버네티스(K8s)나 로드밸런서 환경에서 신규 버전 배포 시 여러 대의 파드(Pod/인스턴스)가 동시에 기동됩니다.
   * 여러 인스턴스가 동시에 기동하며 DDL을 실행하면 DB 락(Lock) 충돌이나 교착 상태(Deadlock)가 발생할 수 있습니다.

### 방식 B. 전용 마이그레이션 도구(Alembic) 기반 관리 (실무 표준)

실무에서는 SQLAlchemy 전용 마이그레이션 도구인 **Alembic**을 사용하여 데이터베이스 스키마를 Git 코드와 함께 버전 관리합니다.

```
[개발자] 모델 변경 (User 엔티티에 컬럼 추가)
   │
   ▼ alembic revision --autogenerate -m "add phone_number to user"
[마이그레이션 스크립트 생성] (alembic/versions/xxxx_add_phone_number.py)
   │
   ▼ Git PR / 코드 리뷰 / Merge
[CI/CD 배포 파이프라인]
   │── 1단계: 배포 전 DB 마이그레이션 선실행 (`alembic upgrade head`)
   └── 2단계: 신규 애플리케이션 파드(Pod) 롤링 업데이트 배포
```

* **장점**:
  1. 모든 DDL 변경 이력이 타임스탬프와 함께 Git 형상 관리되어 추적이 가능합니다.
  2. 장애 발생 시 이전 버전으로 즉시 롤백(`alembic downgrade -1`)이 가능합니다.
  3. 앱 실행 계정에 DDL 권한을 부여하지 않고, 배포 파이프라인의 관리자 권한으로 안전하게 스키마를 선적용할 수 있습니다.

## 3. 실행 스크립트 및 런타임 환경 비교

### 방식 A. `project_run.bat` 스크립트 (현재 방식)

```bat
@echo off
uv run uvicorn app.main:app --host 127.0.0.1 --port 8000 --reload
```

* **적합한 환경**: 윈도우 기반 로컬 개발 환경.
* **장점**: 개발자가 가상환경 활성화나 긴 CLI 옵션을 외울 필요 없이 더블 클릭이나 파일명 입력으로 즉시 개발 서버 구동 가능.
* **주의점**: `--reload` 옵션은 소스 코드 파일 시스템의 변경 감지를 위해 지속적으로 파일 I/O를 수행하므로 CPU/메모리 부하가 크며, 운영 환경에서는 절대 켜지 않습니다.

---

### 방식 B. 컨테이너(Docker) 및 멀티 워커 구동 (실무 표준)

실무 운영 환경에서는 OS나 로컬 의존성에 영향을 받지 않도록 **도커 컨테이너(Docker Container)**로 패키징하여 배포합니다.

#### ① Dockerfile 예시
```dockerfile
FROM python:3.12-slim

WORKDIR /app

# uv 패키지 매니저 복사 및 의존성 설치
COPY --from=ghcr.io/astral-sh/uv:latest /uv /bin/uv
COPY pyproject.toml uv.lock ./
RUN uv sync --frozen --no-dev

# 애플리케이션 소스 복사
COPY . .

# 운영 포트 노출
EXPOSE 8000

# Gunicorn 마스터 프로세스 + Uvicorn 비동기 워커로 구동 (CPU 코어 수 기반 멀티 워커)
CMD ["uv", "run", "gunicorn", "app.main:app", \
     "-k", "uvicorn.workers.UvicornWorker", \
     "-w", "4", \
     "-b", "0.0.0.0:8000", \
     "--access-logfile", "-"]
```

* **Gunicorn + UvicornWorker 조합의 이유**:
  * `uvicorn` 단독 실행 시 단일 프로세스로 동작하므로 서버의 멀티 코어 CPU 자원을 온전히 활용하지 못합니다.
  * `gunicorn`이 프로세스 매니저(Process Manager) 역할을 맡아 워커 프로세스들이 비정상 종료되면 즉시 재생성(Auto-healing)해주며, 각 워커는 고성능 비동기 처리를 위해 `uvicorn.workers.UvicornWorker`를 사용합니다.
  * (단, Kubernetes 환경에서는 Pod 단위로 1코어/1프로세스 Uvicorn을 띄우고 Pod 개수를 HPA로 수평 확장하는 방식을 채택하기도 합니다.)

## 4. 종합 요약 및 단계별 권장 로드맵

| 단계 / 영역 | 애플리케이션 생성 방식 | DB 테이블 스키마 관리 | 서버 구동 환경 |
| :--- | :--- | :--- | :--- |
| **1단계: 프로토타입 / 초기 개발 (현재 단계)** | `app.py` 전역 생성 + `main.py` 진입점 | `lifespan` 내 `create_all()` 자동 생성 | 로컬 `.bat` / `run.sh` (Uvicorn + `--reload`) |
| **2단계: 단위 테스트 및 협업 도입** | `create_app()` 팩토리 함수 도입 | Alembic 도입 준비 (로컬 마이그레이션 생성) | Uvicorn CLI / 가상환경 실행 |
| **3단계: 실무 운영 (Production 배포)** | `create_app()` + 환경별 Settings 주입 | CI/CD 파이프라인 연계 `Alembic upgrade` | Docker 컨테이너 + Gunicorn/K8s 수평 확장 |

### 결론
현재 프로젝트에 구현된 구조는 **기능 중심(Feature-Oriented) 아키텍처와 계층 간 분리(Domain / Feature / Route)를 명확히 학습하고 로컬에서 신속하게 개발**하기에 가장 적절하고 직관적인 방식입니다. 

실제 상용 서비스 런칭 단계로 발전시킬 때는 위 3단계 로드맵에 맞추어 **Factory 패턴, Alembic 마이그레이션, Docker 컨테이너화**를 순차적으로 적용하시면 됩니다.
